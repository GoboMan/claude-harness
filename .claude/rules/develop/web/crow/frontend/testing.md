# 🧪 crow / frontend — テスト設計（外部ランナー）

> **共通則は [common/testing.md](../common/testing.md)**（1テスト=1振る舞い・失敗系を含める・モックは境界だけ・
> 決定性・コマンド一発・命名・カバレッジの扱い）。本書は**それに従ったうえで**、
> frontend 固有の「何を・どこに置いて」テストするかだけを扱う。共通側の再掲はしない。
>
> パーツの構造規約は [viewpart.md](./viewpart.md)、状態と親子の流れは [viewpart-dataflow.md](./viewpart-dataflow.md)。

---

## 1. テストはパーツファイルの中に書かない

ビューパーツのファイルにテストを同居させない。理由は 2 つある。

1. **producer と oracle が同一ファイルになる。** develop は「作る側」と「判定する側」を別コンテキストに分ける。
   テストが実装と同じファイルの別セクションにあると、実装体が自分を判定するテストごと書き換えられてしまい、分離が成立しない
2. **crow が持つパーツ内テスト機構は、コマンド実行と終了コードによる判定に対応していない。**
   結果はブラウザのコンソールに出るだけで、共通則の「実行はコマンド一発」を満たせない

したがって **frontend のテストは、パーツの外にあるテストランナーで回す。**

---

## 2. 検証するロジックは viewpart の外へ切り出す

ビューパーツはブラウザ・DOM・遅延ロードに強く依存するので、そのままでは単体テストしづらい。
**検証したいロジックを「素の JS モジュール」として切り出し、パーツはそれを呼ぶだけにする。**

### 切り出す側（テスト対象）の条件

- **純粋関数にする。** 入力は引数、出力は戻り値。同じ入力なら常に同じ出力
- **DOM を触らない。** `document` / jQuery / `self.ref()` を参照しない
- **viewpart の API に依存しない。** `self.prop()` / `create_child()` を呼ばない
- **グローバルに依存しない。** `g` / `dbc` / `window` / 実時刻 / 乱数を直接読まない。必要なら引数で受け取る

```javascript
//	検証対象：入力を受け取り、値を返すだけ
function build_display_rows( rows_, filter_ )
{
	//	...
	return display_rows;
}
```

### 呼ぶ側（パーツ）の責務

パーツに残すのは **配線だけ**にする。「状態を読む → モジュールを呼ぶ → 状態へ書く」の 3 行で終わる形が理想。

```php
<watch>
{
	rows(old_, new_)
	{
		self.prop('display_rows', build_display_rows(self.prop('rows'), self.prop('filter')));
	}
}
</watch>
```

パーツ側に分岐や計算が溜まってきたら、それは切り出し漏れである。**「この分岐は純粋関数にできないか」を先に疑う。**

---

## 3. 切り出したモジュールの住所と形式を先に決める

切り出したモジュールは **ブラウザ（crow のアセット読み込み）とテストランナー（Node）の両方から読める**必要がある。
この 2 つを満たす形式は環境によって変わるので、**harness 側では固定しない。**

**プロジェクトで次の 3 点を決め、そのプロジェクトの `CLAUDE.md` に記録する。**

1. **住所** — 切り出したモジュールをどのディレクトリに置くか（例: `app/assets/js/<role>/logic/`）
2. **形式** — ブラウザと Node の双方からどう読ませるか（ESM / グローバル関数 / 両対応のいずれか）
3. **実行コマンド** — テストランナーと、全件実行のコマンド 1 本

**決まっていない状態で書き始めない。** test-designer と実装体は別コンテキストで動くため、
住所と形式の解釈が割れると Red と Green が噛み合わず、赤緑ループが組めない。

---

## 4. 何をテストし、何をテストしないか

| 対象 | 扱い |
| --- | --- |
| 切り出した純粋ロジック（整形・判定・変換・バリデーション） | **テストする。** ここが frontend の機械オラクル |
| API クライアント（契約に沿った request/response の組み立て） | **テストする。** バックエンドは契約どおりにモックする |
| 状態遷移のうち、純粋関数に落とせる部分 | **テストする** |
| テンプレートの見た目・CSS | テストしない。人間の一瞥（develop の 🙋 ゲート）で確認する |
| viewpart のライフサイクル・遅延ロード・DOM マウント | テストしない。framework の責務であり、ここを検証しても壊れやすいだけ |

---

## 5. ランナーが未導入なら、それが着手のゲート

crow は**コマンド実行で赤緑を判定できる frontend 用のテストランナーを持たない**ので、
プロジェクトに未導入なら、まず導入する。

導入されていない状態で「テストが無いまま実装だけ進める」のは、develop の Phase4 を成立させないので**やらない**。
選定・設定・実行コマンドは §3 のとおりプロジェクトの `CLAUDE.md` に記録する。
