# ⚙️ crow / backend — コーディング規約（サーバ側の上乗せ）

> **共通スタイルは [common/coding.md](../common/coding.md)**（インデント表・Allman・snake_case・
> `i_` プレフィックス・`===`／`!` 禁止・コメント `//<TAB>`・80 桁・PHP 閉じタグ・ファイル終端改行）。
> 本書は**それに従ったうえで**、サーバ側（action / model / crow API を叩く PHP）にだけ効く差分を定める。
> 共通側の再掲はしない。

## 記法そのものは common に従う

crow の既存コーディング規約を frontend / backend に仕分けた結果、
**「書き方」のレベルでサーバ側にだけ効くルールは無い**（PHP 閉じタグ・`i_` プレフィックスなど
「PHP だから」に見えるものも、crow の view が PHP ファイルである以上 frontend 側も従うため共通に置いた）。

したがって記法は common/coding.md にそのまま従う。
無いルールを埋めるために共通側から写してこないこと（二重化は drift の温床）。
以下で定めるのは記法ではなく **「サーバ側のロジックをどこに書くか」** である。

---

## ドメインロジックの置き場所：モデル拡張が既定

### 前提（crow のモデル生成と拡張点）

- crow は `db_design.txt`（住所と書式は [backend/db.md](./db.md)）のテーブル定義から
  **`model_<table>` クラスを自動生成**する。生成物はキャッシュであり、手で編集する対象ではない。
- そのクラスは **`app/classes/_common_/model_<table>.php`** にユーザ定義クラスを置くと拡張できる。
  crow はこのファイルの **クラス宣言直後（最初の `{` の直後）** に生成メンバ（フィールド・
  `sql_select_all()` / `sql_select_one()`・定数アクセサ・参照テーブル取得）を差し込んでから読み込む。
- ファイルが無ければ標準の生成クラスがそのまま使われる。**拡張はいつでも後から足せる。**

### ルール（必須）

> **そのモデル（＝1 テーブルの行／行集合）だけで完結するドメインロジックは、
> `model_<table>` のメソッドとして定義する。`module_*` 側に書かない。**

理由：module 側に置くとドメインロジックが機能別のモジュールへ散り、
同じ判定・同じ導出が複数の `action_*` に重複して保守できなくなる。
モデルに寄せれば、**そのテーブルの意味を知りたいときに読む場所が 1 つ**になる。

### 判定表（迷ったらここで切る）

| ロジックの性質 | 置き場所 |
| --- | --- |
| 1 行の状態から導かれる派生値・判定・表示用整形（例: `is_rank_upped()`・`period_str()`・料金の導出） | `model_<table>` の **インスタンスメソッド** |
| そのテーブルの行集合に対する検索条件・集計・定型クエリの組み立て | `model_<table>` の **static メソッド**（`sql_select_all()` を起点に組む） |
| 保存前の値の補完・整合チェック・削除時の後始末 | `model_<table>` の **拡張フック**（後述） |
| 複数モデルにまたがる調整、トランザクション境界、リクエスト受けとレスポンス返却 | `module_*` の `action_*` |
| どのテーブルにも属さない純粋なユーティリティ | `app/classes/_common_/` の非モデルクラス |

**「複数モデルにまたがる」の判定を緩めない。** 他モデルを 1 つ参照するだけ（`xxx_row()` で親を引く等）は
まだそのモデルで完結している。`action_*` に残してよいのは、
**複数モデルの更新順序やトランザクションを取り仕切る**場合に限る。

### 拡張ファイルの書き方

```php
<?php

class model_user extends crow_db_table_model
{
	//--------------------------------------------------------------------------
	//	表示用の氏名を組み立てる
	//--------------------------------------------------------------------------
	public function display_name()
	{
		if( $this->name === "" ) return crow_msg::get('db.user.no_name');
		return $this->name;
	}

	//--------------------------------------------------------------------------
	//	有効なユーザだけを引くクエリ
	//--------------------------------------------------------------------------
	public static function sql_select_active()
	{
		return self::sql_select_all()
			->and_where("deleted", 0)
			;
	}
}

?>
```

- クラス名は **`model_<テーブル名>`**、継承は **`crow_db_table_model`**。この 2 つは crow が要求する形。
- **`__construct()` を書かない。** 生成側がコンストラクタを作るため、初期化が要るときは
  **`construct()`** という名前で定義する（生成コンストラクタから呼ばれる）。
- **生成済みメンバを再定義しない。** フィールド、`m_table_name` / `table_name` / `primary_key`、
  `sql_select_all()` / `sql_select_one()`、定数まわりの `get_<field>_keys()` / `_map()` / `_symbols()` /
  `get_<field>_str()` / `<field>_str()`、参照テーブルの `<refer>_row()` は crow が差し込む。
  同名を書くと衝突する。**定型クエリを足すときは `sql_select_all()` を上書きせず別名で生やす。**

### モデルに持ち込まないもの

- **HTTP 層の関心**（`crow_request` からの読み取り、`crow_response`、`app::exit_ok()` / `exit_ng()`、
  リダイレクト）。これは `action_*` の責務。モデルが入出力に依存すると、
  ドメインロジックを単体で呼べなくなり、テストも書けなくなる。
- **画面固有の都合**（特定画面だけの並び順・特定画面だけの文言分岐）。1 画面でしか意味を持たないなら
  それはドメインロジックではない。

> **手書きの**モデルメソッドは入出力から独立しているため、そのまま PHPUnit の単体テスト対象になる。
> crow が差し込む生成メンバはテストしない（切り方は [backend/testing.md](./testing.md)）。

### 保存・検証はフック名が決まっている

保存や削除に絡む処理は `action_*` で前後に挟まず、**モデルの拡張フック**に置く。
`check_and_save()` 等から crow が呼ぶので、どの経路から保存されても必ず効く。

| フック | 用途 |
| --- | --- |
| `validation_crow_ext()` | 追加のバリデーション。失敗は `push_validation_error()` でエラーを積む |
| `save_crow_ext()` | 保存の拡張。失敗時は `push_validation_error()` で積みつつ **`false` を返す** |
| `trash_crow_ext()` | 論理削除の拡張。失敗時は同上 |
| `delete_crow_ext()` | 物理削除の拡張。失敗時は同上 |

`save_ext()` / `validation_ext()` / `trash_ext()`（`_crow_` の無い名前）は
crow 内部のテーブル拡張が使う。**アプリ側で定義しない。**

### 既存コードを触るとき

`action_*` の中に、そのモデルで完結する判定・導出がベタ書きされているのを見つけたら、
**その機能の実装スコープ内にある限りモデル側へ移す**（呼び出し側は 1 行のメソッド呼び出しになる）。
スコープ外のモジュールまで一括で書き換えに行かないこと。
