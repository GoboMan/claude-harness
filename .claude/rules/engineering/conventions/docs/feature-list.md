# 📦 機能一覧の厳格フォーマット

> 機能一覧は **`docs/spec/features.md`** に置く、**全機能を漏れなく列挙した目次**（process.md Phase 1 の最初の成果物）。
> これは他の全作業単位のスコープを決める土台なので、粒度設定に関わらず**常に先行させる**（process.md §2）。
> ここでは `docs/spec/features.md` の**必須フォーマットを厳格に**定める。
> 各機能の詳細は [feature-spec.md](./feature-spec.md)（`docs/spec/<feature>.md`）、配置は [layout.md](./layout.md) を参照。

## なぜ厳格にするか

機能一覧は「何を作るか」の全体集合を宣言する場所。ここに漏れがあると、**存在しないはずの未定義機能が下流で発覚し**、スコープが後からずれる。
機能ID・機能名・状態を機械的に埋めることで、「列挙されていない機能を実装している」事故を防ぐ。

- **「まとめて」＝全部を列挙する意味であり、「凍結」ではない**（process.md §2）。後続が欠陥を暴けば更新される。
- 機能一覧はあくまで**目次**。詳細・GWT・入出力は各 `<feature>.md` に書き、ここには書かない（1 ファイル 1 関心事）。

## 親子関係と機能ID

- 各行の **機能ID は `docs/spec/<feature>.md` および `docs/contracts/<feature>.md` と一致**させる（相互参照の安定キー）。
- 機能ID は `F-000` 形式のゼロ埋め。**新規採番のみ**とし、欠番・再利用しない（ADR 番号と同じ運用）。

## 必須セクション（1つでも欠けたら未完成）

| # | セクション | 内容 |
| --- | --- | --- |
| 1 | メタ | ステータス(`draft`\|`fixed`) / 更新日 |
| 2 | 機能一覧テーブル | 全機能を 1 行 1 機能で列挙。各行に 機能ID / 機能名 / 概要 / 詳細リンク / 状態 |

- **状態**列は各機能詳細（`<feature>.md`）のステータス（`draft` / `fixed`）を反映する。
- 一覧全体の**ステータスが `fixed`** とは、「全機能を出し切った（列挙の網羅が済んだ）」ことを指す。各機能詳細が `fixed` である必要はここでは問わない。

## コピペ用テンプレート

```markdown
---
ステータス: draft        # draft | fixed（列挙の網羅が済んだら fixed）
更新日: YYYY-MM-DD
---

# 機能一覧

| 機能ID | 機能名 | 概要 | 詳細 | 状態 |
| --- | --- | --- | --- | --- |
| F-001 | ログイン | メール＋パスワードで認証する | [F-001](./f-001-login.md) | fixed |
| F-002 | 予約作成 | 予約フォームから予約を登録する | [F-002](./f-002-reserve.md) | draft |
```

## `draft → fixed` チェックリスト

- [ ] メタ（ステータス / 更新日）が埋まっている
- [ ] システムの全機能を洗い出し、漏れなく列挙したか（Phase 1 の網羅）
- [ ] 各行に 機能ID / 機能名 / 概要 / 詳細リンク / 状態 がある
- [ ] 機能ID が `<feature>.md` / `contracts/<feature>.md` と一致している
- [ ] 機能ID が重複・欠番・再利用していない
- [ ] 詳細・GWT・入出力をこの一覧に書き込んでいない（目次に留めている）
