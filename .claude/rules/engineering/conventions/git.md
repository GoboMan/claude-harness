# 📦 Git 規約（commit メッセージ / PR）

> 全開発共通・**platform / framework 非依存**の型。commit メッセージと Pull Request の書き方を定める。
> 進め方の基盤は [process.md](../practices/process.md)。**PR は「1 スライス＝1 ユーザー価値」単位**で出す（縦切りスライス）。
> 仕様・ADR の所在は [docs/layout.md](./docs/layout.md)。PR からは関連 ADR / issue を参照する。

## commit メッセージ規約（Conventional Commits）

### フォーマット

```
<type>(<scope>): <subject>

<body>

<footer>
```

- **type**（必須）と **subject**（必須）以外は任意。`scope` は対象領域（例: `crow`, `docs`）。

### type 一覧

| type | 使う場面 |
| --- | --- |
| `feat` | 機能の追加 |
| `fix` | バグ修正 |
| `docs` | ドキュメントのみ |
| `refactor` | 挙動を変えない内部改善 |
| `test` | テストの追加・修正 |
| `perf` | パフォーマンス改善 |
| `style` | 整形のみ（ロジック不変） |
| `build` / `ci` | ビルド・CI 設定 |
| `chore` | その他雑務（依存更新など） |

### subject（要約行）のルール

- **1 コミット＝1 論理変更**。整形とロジック変更を混ぜない。
- 命令形・現在形で書く（「〜する」「add」）。末尾にピリオドを付けない。
- 目安 50 文字程度。何を変えたかが一目で分かること。
- 言語はチームで統一（日本語の subject 可。ただし `type` は英語）。

### body / footer

- **body**: なぜ変えたか・背景を書く（何を変えたかは diff を見れば分かる）。1 行 72 文字程度で折り返す。
- **footer**:
  - 関連 issue / ADR を参照: `Refs: #123` / `ADR-0007`
  - 破壊的変更: `BREAKING CHANGE: <説明>`
  - AI が関与したコミットは `Co-Authored-By:` トレーラを付けてよい（任意）。

### 例

```
feat(crow): 予約フォームの入力検証を追加

未入力・桁あふれ・不正文字を弾く。GWT の失敗系ケースに対応。
入力値は i_ 変数として受け、check_value で判定する。

Refs: #142
```

## Pull Request 規約

- **1 PR＝1 スライス（1 ユーザー価値）。** 大きくせず、レビュー可能な単位に保つ。常に E2E で 1 本通る状態で出す。
- **タイトル**は commit と同じ規約（`type(scope): 要約`）に揃える。
- 本文は下記テンプレートに従う。プロジェクトでは `.github/pull_request_template.md` として配置する。

### PR テンプレート

```markdown
## 目的 / Why
<!-- この PR で達成すること。解決する課題。 -->

## 変更点 / What
-

## スライス
<!-- どのユーザー価値を縦貫させたか。E2E で通る 1 本か。 -->

## テスト
- [ ] 追加/更新したテストと観点（失敗・空・境界・権限を含む）
- [ ] ローカルで緑（テスト緑は前提であって完成条件ではない）

## 関連
- Issue: #
- ADR: ADR-XXXX

## セルフレビュー
- [ ] 1 スライス（1 価値）に絞られている
- [ ] コーディング規約に沿っている
- [ ] 仕様変更は docs/spec を正として更新した
```

## ✅ commit / PR 前チェックリスト

- [ ] このコミットは 1 論理変更か（整形とロジックを混ぜていないか）
- [ ] subject が命令形・簡潔で、`type` が適切か
- [ ] 破壊的変更・関連 issue / ADR を footer に書いたか
- [ ] PR は 1 スライスに絞られ、E2E で通るか
- [ ] PR テンプレートの各項目を埋めたか
