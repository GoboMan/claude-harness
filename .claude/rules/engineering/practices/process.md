# AI駆動開発プロセス — 核（常時ロード）

> このドキュメントは、AIエージェントがシステム開発を進める際の**不変の核**である。**開発着手時に必ず最初に読む。**
> 粒度の決め方・フェーズ別手順・各サブエージェントの台本といった**実行の詳細**は、その局面に来た時に [process-agents.md](./process-agents.md) の該当節を都度ロードする（常時は読まない）。
> 節番号は2ファイル通しで一意。**核＝§0–§2・§6／実行台本＝§3–§5**。

---

## 0. 読み方と原則

- **コア制約（§1）は絶対に守る。** 粒度や手順を変えても違反してはならない。
- **粒度は固定値ではなく、案件ごとに宣言して決める設定値である。** プロジェクト／サブシステム単位で設定する（設定手順は process-agents.md §3）。
- **成果物を作った主体と、それを判定する主体は、別コンテキストにする。** 作った本人がチェックすると同じ見落としを繰り返すため、見落としが重ならないよう役割を分ける。これが本プロセスの最重要原則であり、複数のサブエージェントに分割する理由そのものである。

---

## 1. コア制約（ハード制約 / 違反禁止）

以下は粒度をどう設定しても変えてはならない。

1. **SSOT（信頼できる唯一の情報源 / Single Source of Truth）が実装に先行する。** コードは真実の源にならない。実装が仕様の欠陥を暴いたら、コードを正とせず SSOT を更新する（差し戻しルールは process-agents.md §4）。
2. **受け入れ条件は反証可能・実装非依存で書く。** Given-When-Then 形式。「何を満たせば正しいか」ではなく「何が観測されたら誤りと分かるか」を判定できる粒度にする。
3. **完成の判定は、独立した判定役（オラクル）が行う。** 成果物を作ったエージェント自身に「仕様と一致したか」を判定させない。
4. **最終ゲートは『テストが通った』ではなく『壊しにいって壊れなかった』である。** 本番に最も近い環境（実データ・実I/O・E2E・探索的な攻撃）でシステムを壊そうと試み、壊れなかったことをもって完成とする。テストが緑（全通過）なのは前提条件であって、完成条件ではない。
5. **どの作業単位も必ず `定義 → 構造の整合 → 振る舞いの整合 → 壊しにいく` の順を通る。** この順序は粒度を変えても保たれる。
6. **UIとバックエンド処理は、共有する「処理インターフェース契約（request / response の形）」を先に固定してから作る。** 契約は構造整合フェーズ（process-agents.md §4 Phase 3）の成果物であり、UI実装と処理実装はどちらもこの契約だけを拠り所に、別コンテキストで作る。**契約が固定される前にUIを作らない**（後工程で処理を作った時にUIが合わず手戻りする、最大の原因を断つため）。

## 1.5 実装着手ゲート（コードを書く前に必ず通す）

> コア制約1（SSOT 先行）を、**着手の瞬間に発火する停止線**にしたもの。理念ではなく手続きである。
> **このゲートを通さずに、実装・DB スキーマ・契約に対応するコードを触ることを禁止する。**
> （なぜ設けたか: 「既存パターンに似た小さな CRUD だから」と Phase 1 を飛ばして実装へ直行し、未仕様の機能を作ってしまう事故が実際に起きたため。）

実装・DB スキーマ・契約に対応するコードを**一文字でも書く／変更する前**に、対象機能について次を確認する。

1. **列挙されているか** — `docs/spec/features.md` に対象機能が載っているか。
2. **仕様が fixed か** — `docs/spec/<feature>.md` が存在し、ステータスが `fixed` か。
3. **契約が fixed か** — `docs/contracts/<feature>.md` が存在し、ステータスが `fixed` か。

**1つでも欠けたら、あなたは Phase 4（実装）ではなく Phase 1（定義）にいる。** 実装を止め、全体フロー(§2)の①へ戻り、SSOT を作る／`fixed` にしてから戻ること。

### 免除にならない言い訳（すべて却下）

- 「既存の〈別機能〉と同じパターン／コピペで作れるから」 — パターンの一致は仕様の存在を意味しない。
- 「小さい CRUD だから」「1 画面・1 テーブルだけだから」 — 規模はゲートを免除しない。
- 「稼働中プロジェクトへの追加だから Phase 1 は済んでいるはず」 — features.md は**その機能が載っている時だけ**済んでいる。既存一覧に無い機能は、新規採番（F-xxx）から始まる**新機能**である。
- 「ユーザーが『実装して』と言ったから」 — 依頼は「動くもの」への依頼であって、SSOT を飛ばす許可ではない。仕様が無ければ、**まず仕様を作ることが依頼への正しい応答**（勝手に実装で応えない）。

### 通過の記録と機械裏取り

新機能なら、features.md に採番・追記し、`<feature>.md` と `contracts/<feature>.md` を作って**人間の確認で `fixed`** に上げてから Phase 4 に入る。
機械検証は [spec-lint](../conventions/enforcement/spec-lint.md) の `gate`（commit 時・`Feature:` トレーラ）で裏取りできるが、**それは commit まで発火しない事後チェックにすぎない。本ゲートは着手前に自分で通すもの**であり、機械強制の有無に関わらず省略しない。

## 2. 全体フロー

```
① まとめて固める（基準SSOT・凍結ではない）
   └ 機能一覧・機能詳細（全機能を先に列挙／反証可能なGWT）
        │
   [Gate] 構造リスク判定 ──→ 粒度と skeleton の要否を決定
        │
   (条件付き) ウォーキングスケルトン（高リスク時のみ）
        │
② 縦切りで実装する（機能スライスごとに反復）
   ├ 構造の整合（機能 × DB × 処理インターフェース契約 × UI骨格）  ← 契約をここで固定
   ├ 振る舞いの実装（契約を共有する2トラック・スライス内で並行）
   │    ├ 4a UI実装    （契約に沿う。応答は契約通りにモック）
   │    └ 4b 処理実装  （契約に沿う。Red → Green → Refactor）
   │        └→ 契約で突き合わせて結合
   └ スライス単位で壊しにいく
        │
   スライス横断で壊しにいく ＋ 横断的な非機能要件（相互作用から生じる不整合の検出）
        │
   完成

　※ ①と②の間で見つかった欠陥は「基準SSOTへ差し戻す」（影響範囲で戻り先を分岐）
```

- **①（まとめて固める）** は定義フェーズ。機能一覧・機能詳細は全機能を先に出し切る。これは他の全作業単位のスコープを決める土台なので、粒度設定に関わらず常に先行させる。「まとめて」＝全部を列挙する意味であり、「凍結」ではない。後続が欠陥を暴けば更新される。
- **②（スライス実装）** はバッチサイズ（1回に扱う作業量）が可変な領域。構造整合の粒度だけがリスク依存で動く。振る舞いの実装より下は、どの案件でも縦切りが基本。
- **UIと処理は「スライス内の2トラック」に分ける。** 先に固定した契約を共有しつつ、UI実装と処理実装を別コンテキストで並行させ、AIが一度に考える対象をUI／処理に二分する。ただし分けるのはスライスの内側だけであり、「全機能のUIを作ってから全機能の処理を作る」横積みにはしない（縦切りスライスの原則＝常にE2Eで1本通る、を維持する）。

## 6. 完成条件（最終ゲート）

以下がすべて満たされた時のみ「完成」とする。

- [ ] 全機能が基準SSOTに列挙され、各機能に反証可能な GWT がある。
- [ ] Phase 3 で各機能の処理インターフェース契約が確定し、構造整合オラクルが参照・契約の不整合を発見できない。
- [ ] 全スライスで UI・処理がともに契約に適合し、テスト緑、かつ結合後に機能詳細と整合。
- [ ] 攻撃エージェントがどのスライスも壊せなかった。
- [ ] 横断反証エージェントが、相互作用から生じる不整合・NFR違反を発見できなかった。
- [ ] 実装中に発生した全 SSOT 変更が差し戻し処理され、影響を受けるスライスが再検証済み。

**「テストが全部通ったから完成」は完成条件ではない。** 独立した攻撃を本番に最も近い環境で試みて壊れなかったことが、唯一の完成条件である。
