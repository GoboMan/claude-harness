## 3. 粒度の調整とリスク判定

> ロードするタイミング: Gate（構造リスク判定）で粒度と skeleton の要否を決める時。

### 決定変数

構造リスク（＝「振る舞いを作る前に、構造がどれだけ静的に分かっているか」）で粒度が決まる。判断材料は3つ。

- **ドメイン既知度** — 標準的な業務オブジェクト（案件・人材管理の CRUD 等）か、前例の少ない新規の構造か。
- **構造変更の影響範囲（blast radius）** — 1箇所直すと何機能に波及するか。
- **手戻りコストの偏り** — 本番データ投入済み等で、スキーマ変更が特に高くつく状態か。

### 決定則

```
リスク値 = P(振る舞いを作って初めて露見する構造欠陥が存在する)
         × 全体を固めた後にそれが発覚した時の改修コスト

リスク値 低 → 粗い粒度（構造整合をサブシステム単位でまとめて固める）
リスク値 高 → 細かい粒度（構造整合もスライスに繰り延べ ＋ skeleton を先に通す）
```

### デフォルトは粗粒度に寄せる（重要）

**「柔軟に対応する＝常に細かく刻む」ではない。** デフォルトは粗いままにし、細粒度は「リスクが高いときの例外」とする。既知ドメインで細粒度をデフォルトにすると、機能横断を早期に見渡せる利点を失い、調整コストだけを払うことになる。

粒度は**プロジェクト単位ではなくサブシステム単位**で変わりうる。同一プロジェクト内でも、既知の CRUD 部分（粗）と新規性の高い部分（細）は別々に宣言する。

## 4. フェーズ別の手順と差し戻しルール

> ロードするタイミング: 各フェーズを実際に進める時／SSOT変更で差し戻す時。

### Phase 1 — 基準SSOT定義（まとめて固める）
- 全機能を列挙し、機能詳細と反証可能な GWT 受け入れ条件を書く。
- **起動**: `SSOT定義エージェント`（§5-A）
- **完了条件**: 全機能が列挙され、各機能に反証可能な GWT が付与され、ハッピーパス以外の状態（error / loading / empty / 権限 / 境界）も受け入れ条件に含まれている。

### Gate — 構造リスク判定
- 各サブシステムのリスク値を出し、粒度と skeleton の要否を決定（判定基準は §3）。
- **起動**: `構造リスク判定エージェント`（§5-B）

### Phase 2 — ウォーキングスケルトン（条件付き・高リスク時のみ）
- 最もリスクの高い機能横断パスを1本だけ、最小実装で端から端まで（E2E）貫通させ、「この構造は振る舞いを支えられるか」を検証。
- **起動**: `スケルトンエージェント`（§5-C）
- ここを通せば、残りの構造は正当に粗いモードで固めてよい。

### Phase 3 — 構造整合ループ（スライス）
- 機能に対応する DB・**処理インターフェース契約（request / response）**・UI骨格 を作り、参照整合（互いに正しく参照し合う状態）を取る。契約は UI と処理の境界を固定する第一級の成果物で、後続の UI 実装・処理実装が唯一の拠り所とする。
- **起動**: `構造整合ビルダー`（§5-D）→ 完了後に別コンテキストで `構造整合オラクル`（§5-E）
- **完了条件**: オラクルが参照の不整合を1件も発見できなくなるまで反復（全機能が実在するエンティティを参照、全画面が実在する機能を参照、**契約が全機能の入出力を過不足なく表現している** 等）。判定はビルダー自身にさせない。

### Phase 4 — 振る舞い実装ループ（スライス・契約を共有する2トラック）
Phase 3 で固定した処理インターフェース契約を土台に、UIと処理を別コンテキストで並行実装する。AIが一度に考える対象をUI／処理に二分し、それぞれに集中させる。

- **Phase 4a — UI実装**: 契約の request / response に沿って UI を作る。バックエンド応答は契約通りにモックする。**起動**: `UI実装エージェント`（§5-G1）。
- **Phase 4b — 処理実装**: 契約の request / response に沿って、バックエンドのリクエスト処理を Red → Green → Refactor で作る。**起動**: `処理実装エージェント`（§5-G2）。
- **結合**: 4a と 4b を契約で突き合わせて結合する。両者が契約を守っていれば食い違わない。
- **起動順**: `テスト設計エージェント`（§5-F, 独立。契約とGWTからUI用・処理用の両テストを起こす）→ 4a / 4b（別コンテキストで並行）→ 契約で結合 → スライス完了ごとに `攻撃エージェント`（§5-H）。
- **重要**: テストは GWT と契約から起こす。実装を見て書かせない。テスト設計・UI実装・処理実装はすべて別コンテキストにし、誤りが重ならないようにする。契約を変えたくなったら実装を止め、Phase 3 へ差し戻す（下記 差し戻しルール）。
- **完了条件**: UI・処理とも契約に適合し、結合後に各機能を機能詳細と照合して整合。スライスを壊しにいっても壊れない。

### Phase 5 — スライス横断で壊しにいく ＋ 横断的な非機能要件（NFR）
- スライス単位では原理的に拾えない、スライス間の相互作用・性能・セキュリティ・a11y 等、相互作用から生じる不整合を潰す。
- **起動**: `横断反証エージェント`（§5-I）

### 差し戻しルール（影響範囲で戻り先を分岐）

実装中に SSOT 変更が必要になったら、**一旦実装を止めて SSOT を直してから戻る。** 戻り先は変更の影響範囲で分岐する。

| 変更の種類 | 戻り先と再検証範囲 |
|---|---|
| 振る舞いだけの SSOT 変更 | 現在のスライスに戻る |
| 固めた構造に触る SSOT 変更 | ①基準SSOTを更新 → 該当スコープの構造整合（Phase 3）を再実行 → **完了済みスライスの整合も再検証** |

「一律で元のループへ戻す」は禁止。構造変更が過去のスライスを黙って壊すため。影響範囲の判定は §5-J に委ねる。

## 5. サブエージェント定義

> ロードするタイミング: 各サブエージェントを起動する時。**起動するものの項だけ**を読めばよい。
> 各エージェントは**別コンテキスト**で起動する。親は入力として SSOT の該当部分を渡す。ミッションは命令として与える。

### A. SSOT定義エージェント
- **起動**: Phase 1 冒頭。
- **ミッション**: 「システムの全機能を漏れなく列挙せよ。各機能に、反証可能で実装非依存な Given-When-Then の受け入れ条件を付けよ。ハッピーパスだけでなく、失敗・空・権限・境界の状態も条件に含めよ。実装方法には一切言及するな。」
- **独立性**: —
- **出力**: 機能一覧、機能詳細、GWT 受け入れ条件（＝基準SSOT）。

### B. 構造リスク判定エージェント
- **起動**: Phase 1 完了後、Phase 3 開始前。
- **ミッション**: 「各サブシステムについて、ドメイン既知度・構造変更の影響範囲・手戻りコストの偏りを評価し、リスク値を出せ。リスク値から構造整合の粒度（まとめて／スライス）と、ウォーキングスケルトンの要否を決定せよ。デフォルトは粗粒度とし、細粒度はリスクが正当化する場合のみ選べ。」
- **出力**: サブシステム別の粒度設定と skeleton の要否。

### C. スケルトンエージェント（条件付き）
- **起動**: Gate で高リスクと判定されたサブシステムに対してのみ。
- **ミッション**: 「最もリスクの高い機能横断パスを1本だけ選び、必要最小限の実装で端から端まで E2E で貫通させよ。目的は機能の完成ではなく『この構造が実際の振る舞いを支えられるか』の検証だ。支えられないなら、構造を固める前にここで露見させろ。」
- **出力**: 貫通の成否と、構造に対する反証（あれば差し戻す）。

### D. 構造整合ビルダー
- **起動**: Phase 3、宣言された粒度の単位で。
- **ミッション**: 「基準SSOTの機能に対応する DB スキーマ、処理インターフェース契約（各機能の request / response の形）、UI骨格を作れ。機能・DB・契約・UI が互いに整合して参照し合う構造を組め。契約は UI と処理の境界を固定する成果物であり、後続の UI 実装と処理実装が唯一の拠り所とする。UI・処理の中身はまだ作らず、境界の形だけを確定させよ。」
- **出力**: DB設計、処理インターフェース契約、UI骨格。

### E. 構造整合オラクル（独立判定）
- **起動**: 構造整合ビルダー完了後、**必ず別コンテキストで**。
- **ミッション**: 「お前の仕事は一致を確認することではない。**不整合を探し出すことだ。** 実在しないエンティティを参照している機能、実在しない機能に紐づく画面、どのデータモデルからも導出できない UI 状態、機能詳細が要求するのに構造が表現できないケース、**契約（request / response）が表現できていない入出力、契約にあるのにどの機能も使わないフィールド** を、片っ端から暴け。一件も見つからなくなるまで、整合しているという主張を疑い続けろ。」
- **独立性**: ビルダーと別コンテキスト必須。
- **出力**: 不整合リスト（空になるまでビルダーへ差し戻し）。

### F. テスト設計エージェント（独立）
- **起動**: Phase 4、各スライスの実装前。
- **ミッション**: 「この機能の GWT 受け入れ条件と処理インターフェース契約から、UI用・処理用のテストケースをそれぞれ書け。**実装コードは見るな。** 意図をエンコードしたテストを書くのであって、実装に合わせたテストを書くのではない。ハッピーパスに加え、失敗・境界・異常入力のケースを網羅せよ。UIテストは契約通りの応答を前提に、処理テストは契約通りの入出力を前提に書け。」
- **独立性**: UI実装・処理実装の各エージェントと別コンテキスト必須。
- **出力**: 失敗する（Red）テスト群（UI用・処理用）。

### G1. UI実装エージェント（Phase 4a）
- **起動**: テスト設計エージェント完了後。処理実装エージェントとは別コンテキストで並行。
- **ミッション**: 「処理インターフェース契約の request / response に沿って UI を実装せよ。バックエンド応答は契約通りにモックせよ。与えられた UI テストを Red → Green → Refactor で満たせ。契約を勝手に変えるな。契約に不足を見つけたら実装を止め、Phase 3 へ差し戻せ。」
- **独立性**: 処理実装エージェントと別コンテキスト必須。
- **出力**: UI実装（UIテスト緑、契約準拠）。

### G2. 処理実装エージェント（Phase 4b）
- **起動**: テスト設計エージェント完了後。UI実装エージェントとは別コンテキストで並行。
- **ミッション**: 「処理インターフェース契約の request / response に沿って、バックエンドのリクエスト処理を実装せよ。与えられた処理テストを Red → Green → Refactor で満たせ。テストを弱めたり、テストに合わせて契約や仕様を歪めたりするな。契約に不足を見つけたら実装を止め、Phase 3 へ差し戻せ。実装後、機能詳細と照合して整合を取れ。」
- **独立性**: UI実装エージェントと別コンテキスト必須。
- **出力**: 処理実装（処理テスト緑、契約準拠）。

### H. 攻撃エージェント（スライスを壊しにいく / レッドチーム）
- **起動**: Phase 4、各スライス実装完了ごと。
- **ミッション**: 「お前はこのスライスを徹底的に攻撃しろ。あらゆる弱い部分を突いてシステムを壊そうとしろ。不正入力、境界値、競合状態、権限の回避、想定外の順序での操作、実データの汚れ ── 開発者が『通るはず』と思い込んだ経路をすべて疑い、壊せ。壊せたら、それは実装か SSOT の欠陥だ。報告し、差し戻せ。壊せなかった時だけ、このスライスを通過とする。」
- **独立性**: 実装エージェントと別コンテキスト必須。
- **出力**: 破壊に成功した攻撃の一覧（欠陥として差し戻し）。

### I. 横断反証エージェント（Phase 5 / レッドチーム）
- **起動**: 全スライス完了後、完成の直前。
- **ミッション**: 「お前は個々のスライスではなく、**システム全体とスライス間の相互作用**を攻撃しろ。あるスライスが別のスライスの前提を壊す経路を探せ。性能（負荷・レイテンシ）、セキュリティ（認証・認可・注入・情報漏洩）、a11y、データ整合の破れを、実データと本番相当の環境で突け。特定の機能に紐づかず誰も見ていない横断的な非機能要件（NFR）こそ狙え。ここで壊れなかった時に初めて完成だ。」
- **独立性**: これまでの全ビルダーと別コンテキスト必須。
- **出力**: 相互作用から生じる不整合・NFR違反の一覧。

### J. 差し戻し・再整合エージェント
- **起動**: 任意のフェーズで SSOT 変更が必要になった時。
- **ミッション**: 「この SSOT 変更の影響範囲を判定せよ。振る舞いだけの変更なら現スライスに戻す。固めた構造に触る変更なら、基準SSOTを更新し、該当スコープの構造整合を再実行し、**完了済みスライスの整合も再検証**せよ。過去のスライスが黙って壊れていないことを確認するまで、完了扱いにするな。」
- **出力**: 更新後の SSOT、再検証すべきスライスの一覧。
