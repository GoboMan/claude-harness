# 🎼 develop — 開発の指揮者（orchestrator）

> **このスキルを起動した時点で、あなた（メインエージェント）は orchestrator である。**
> あなたは原則コードを書かない。**SSOT を正とし、専門サブエージェント（`.claude/agents/develop/`）を Task ツールで順に起動し、停止・報告を受けて分岐する指揮者**に徹する。
> 各エージェントの人格は `.claude/agents/develop/*.md`。**本 SKILL は orchestrator の判断核（§0–§2・§6–§7）と実行台本（§3–§5）を自己完結で内包する**（orchestrator だけが読むため、rules に置かずここへ一元化）。節番号は本書で一意。

## orchestrator の不変則

- **自分でコードを書かない。** 作るのはサブエージェント、判定は独立役。**作る主体と判定する主体を別コンテキストにする**（それぞれ別に Task 起動する）。
- **自分で git を叩かない。** commit / PR は `committer` に委譲する。あなたは差分を作らず・実行せず、「何を・なぜ・関連 ID（Feature/Issue/ADR）」の意図だけを渡す管理者に徹する。
- **設計決定の記録（ADR）も自分で書かず `adr-writer` に委譲する**（決定コンテキストを渡す）。
- **人間と話せるのはあなただけ。** 次の3つ（人間オラクル成果物）の**作成・変更は必ず人間の承認を得る**（AskUserQuestion / plan mode）:
  1. **SSOT**（機能一覧・機能詳細／GWT）
  2. **UI の見た目**
  3. **DB 設計**
- **それ以外（契約・純粋関数・テスト・実装・結合）は SSOT を正として機械＋AIで回す**（人間を挟まない）。SSOT を正とすれば決定論的に反証可能（テスト・型・lint・spec-lint・参照整合）だからだ。

## 0. 読み方と原則

- **コア制約（§1）は絶対に守る。** 手順や刻み方を変えても違反してはならない。
- **成果物を作った主体と、それを判定する主体は、別コンテキストにする。** 作った本人がチェックすると同じ見落としを繰り返すため、見落としが重ならないよう役割を分ける。これが本プロセスの最重要原則であり、複数のサブエージェントに分割する理由そのものである。

---

## 1. コア制約（ハード制約 / 違反禁止）

以下は手順や刻み方を変えても変えてはならない。

1. **SSOT（信頼できる唯一の情報源 / Single Source of Truth）が実装に先行する。** コードは真実の源にならない。実装が仕様の欠陥を暴いたら、コードを正とせず SSOT を更新する（差し戻しルールは §4）。
2. **受け入れ条件は反証可能・実装非依存で書く。** Given-When-Then 形式。「何を満たせば正しいか」ではなく「何が観測されたら誤りと分かるか」を判定できる粒度にする。
3. **完成の判定は、独立した判定役（オラクル）が行う。** 成果物を作ったエージェント自身に「仕様と一致したか」を判定させない。オラクルには2種類ある ── **機械オラクル**（テスト・型・lint・スキーマ検証で反証できる成果物＝契約・純粋関数・処理・テスト。人間を挟まず自律で緑まで回す）と、**人間オラクル**（機械では反証できない成果物＝機能要件・UI・DB設計。人間確認で `fixed` 化する）。どちらのオラクルも producer とは別主体にする。サブエージェントの実体は §5・`.claude/agents/develop/*.md`。
4. **最終ゲートは『テストが通った』ではなく『壊しにいって壊れなかった』である。** 本番に最も近い環境（実データ・実I/O・E2E・探索的な攻撃）でシステムを壊そうと試み、壊れなかったことをもって完成とする。テストが緑（全通過）なのは前提条件であって、完成条件ではない。
5. **どの作業単位も必ず `定義 → 構造の整合 → 振る舞いの整合 → 壊しにいく` の順を通る。** この順序はどんな刻み方でも保たれる。
6. **UIとバックエンド処理は、共有する「処理インターフェース契約（request / response の形）」を先に固定してから作る。** 契約は構造整合フェーズ（§4 Phase 3）の成果物であり、UI実装と処理実装はどちらもこの契約だけを拠り所に、別コンテキストで作る。**契約が固定される前にUIを作らない**（後工程で処理を作った時にUIが合わず手戻りする、最大の原因を断つため）。

## 1.5 実装着手ゲート（コードを書く前に必ず通す）

> コア制約1（SSOT 先行）を、**着手の瞬間に発火する停止線**にしたもの。理念ではなく手続きである。
> **このゲートを通さずに、実装・DB スキーマ・契約に対応するコードを触ることを禁止する。**
> （なぜ設けたか: 「既存パターンに似た小さな CRUD だから」と Phase 1 を飛ばして実装へ直行し、未仕様の機能を作ってしまう事故が実際に起きたため。）

実装・DB スキーマ・契約に対応するコードを**一文字でも書く／変更する前**に、対象機能について次を確認する。

1. **列挙されているか** — `docs/spec/features.md` に対象機能が載っているか。
2. **仕様が fixed か** — `docs/spec/<feature>.md` が存在し、ステータスが `fixed` か。
3. **契約が fixed か** — `docs/contracts/<feature>.md` が存在し、ステータスが `fixed` か。

**1つでも欠けたら、あなたは Phase 4（実装）ではなく Phase 1（定義）にいる。** 実装を止め、全体フロー(§2)の①へ戻り、SSOT を作る／`fixed` にしてから戻ること。

### 免除にならない言い訳（すべて却下）

- 「既存の〈別機能〉と同じパターン／コピペで作れるから」 — パターンの一致は仕様の存在を意味しない。
- 「小さい CRUD だから」「1 画面・1 テーブルだけだから」 — 規模はゲートを免除しない。
- 「稼働中プロジェクトへの追加だから Phase 1 は済んでいるはず」 — features.md は**その機能が載っている時だけ**済んでいる。既存一覧に無い機能は、新規採番（F-xxx）から始まる**新機能**である。
- 「ユーザーが『実装して』と言ったから」 — 依頼は「動くもの」への依頼であって、SSOT を飛ばす許可ではない。仕様が無ければ、**まず仕様を作ることが依頼への正しい応答**（勝手に実装で応えない）。

新機能なら、features.md に採番・追記し、`<feature>.md` と `contracts/<feature>.md` を作って**人間の確認で `fixed`** に上げてから Phase 4 に入る。機械検証は spec-lint ツール（`.claude/tools/spec-lint/spec-lint.mjs gate`。commit 時・`Feature:` トレーラ）で裏取りできるが、**それは commit まで発火しない事後チェックにすぎない。本ゲートは着手前に自分で通すもの**であり、機械強制の有無に関わらず省略しない。

## 2. 全体フロー

```
① まとめて固める（基準SSOT・凍結ではない）
   └ 機能一覧・機能詳細（全機能を先に列挙／反証可能なGWT）
        │
   [Gate] 構造リスク判定 ──→ skeleton の要否を決定（高リスク部分だけ）
        │
   (条件付き) ウォーキングスケルトン（高リスク時のみ）
        │
② 縦切りで実装する（機能スライスごとに反復）
   ├ 構造の整合（機能 × DB × 処理インターフェース契約）  ← 契約をここで固定（UI設計書は作らない）
   ├ 振る舞いの実装（契約を共有する frontend/backend 2トラック・スライス内で並行）
   │    ├ 4a frontend （見た目 → 配線 の順。見た目はモック応答、配線は Red→Green）
   │    └ 4b backend  （契約に沿う。Red → Green → Refactor）
   │        └→ 契約で突き合わせて結合
   └ スライス単位で壊しにいく
        │
   スライス横断で壊しにいく ＋ 横断的な非機能要件（相互作用から生じる不整合の検出）
        │
   完成

　※ ①と②の間で見つかった欠陥は「基準SSOTへ差し戻す」（影響範囲で戻り先を分岐）
```

- **①（まとめて固める）** は定義フェーズ。機能一覧・機能詳細は全機能を先に出し切る。これは他の全作業単位のスコープを決める土台なので、常に先行させる。「まとめて」＝全部を列挙する意味であり、「凍結」ではない。後続が欠陥を暴けば更新される。
- **②（スライス実装）** は縦切りが基本。ただしリスクの高い構造だけは、本格実装の前に skeleton で1本 E2E 貫通させて妥当性を先に暴く（要否判定は §3）。
- **frontend と backend は「スライス内の2トラック」に分ける。** 先に固定した契約を共有しつつ、両者を別コンテキストで並行させ、AIが一度に考える対象を二分する。さらに frontend トラックは「見た目（html/css/js・モック応答）→ 配線（リクエスト処理・純粋関数）」に分け、見た目だけを先に作れるようにする（オラクルが違う: 見た目は人間の一瞥、配線は機械テスト）。ただし分けるのはスライスの内側だけであり、「全機能の見た目を作ってから全機能の処理を作る」横積みにはしない（縦切りスライスの原則＝常にE2Eで1本通る、を維持する）。
- **用語**: 本書の「frontend 処理／backend 処理」は、各実装 agent 名の「ロジック」（`frontend-logic-implementer` / `backend-logic-implementer`）と**同義**——リクエスト処理・状態・入力検証・純粋関数を指す。「見た目」（マークアップ・スタイル）とは別物。

## 3. ウォーキングスケルトンの要否（構造リスクの見極め）

> 使うタイミング: Gate（Phase1 完了後・Phase3 開始前）で skeleton の要否を決める時。

構造整合を本格的に進める前に、「振る舞いを作って初めて露見する構造欠陥」のリスクが高い部分だけ、ウォーキングスケルトンで先に潰す。次のいずれかに当てはまる構造は**高リスク**とみなし、skeleton を先に通す：

- **新規性が高い** — 標準的な業務オブジェクトの CRUD ではなく、前例の少ない構造。
- **影響範囲（blast radius）が広い** — 1箇所直すと多くの機能に波及する。
- **手戻りコストが高い** — 本番データ投入済み等で、スキーマ変更が特に高くつく。

**デフォルトは skeleton なしで Phase3 へ進む。** 上記に該当する部分だけ例外的に skeleton を挟む（既知パターン、例えば crow の CRUD は不要）。判定は orchestrator インライン（§5-B）。

## 4. フェーズ別の手順と差し戻しルール

### docs 成果物の住所（全 Phase 共通）

各フェーズの成果物は `docs/` の固定の住所に置く。**書式（フォーマット）は rules に置かず、各成果物を生成する producer の craft（agent body）が持つ。**

| 成果物 | 置き場所 | 書式の所有（craft） |
| --- | --- | --- |
| 機能一覧 | `docs/spec/features.md` | `ssot-definer` |
| 機能詳細 ＋ GWT（基準SSOT） | `docs/spec/<feature>.md` | `ssot-definer` |
| 処理インターフェース契約 | `docs/contracts/<feature>.md` | `contract-author` |
| DB 設計 | **framework/project が定める住所・書式**（§6 の規約が指定。規約が無ければ `docs/db/schema.md` にドラフト） | `db-designer` ＋ framework 規約 |
| アーキテクチャ決定記録（ADR） | `docs/adr/NNNN-YYYY-MM-DD-title.md` | `adr-writer` |

- 固定するのは全プロジェクト共通の最小骨格だけ。案件固有の docs は各プロジェクトの `docs/` に自由に足してよい。
- **DB 設計の住所・書式は develop 側で固定しない。** framework/project がマイグレーション元となるネイティブ形式を持つなら（例: crow の `db_design.txt`＝そこから直接マイグレーション生成）、**その1ファイルを唯一の SSOT** とし、`schema.md` 等へ写し替えて二重管理しない（SSOT を割らない）。ネイティブ形式が無い時だけ中立ドラフトを `docs/db/` に置く。住所・書式は §6 の framework 規約が供給し、`db-designer` に渡す。
- **SSOT は実装に先行する。** 実装が仕様の欠陥を暴いたら、コードでなく SSOT（`docs/spec/` ／ DB 設計元ファイル）を更新する。1 ファイル 1 関心事、参照は相対パス。

### Phase 1 — 基準SSOT定義（まとめて固める）
- 全機能を列挙し、機能詳細と反証可能な GWT 受け入れ条件を書く。
- **入力**: orchestrator が対象スコープ（何を作る/変えるか）を渡す（新規は agent がスコープから起こす。更新時は既存 SSOT のパスも渡し、差分で更新させる）。
- **起動**: `ssot-definer`（§5-A）。**機能数が多いときは分割起動してよい**: まずスコープを「機能一覧の列挙のみ」に絞って 1 回起動し、列挙が出たら**機能詳細を機能単位の並行 Task で N 体起動**する（1 機能 1 ファイルなので独立に書ける）。人間承認は従来どおり一覧＋詳細をまとめて 1 回（承認回数は増やさない）。
- **完了条件**: 全機能が列挙され、各機能に反証可能な GWT が付与され、ハッピーパス以外の状態（error / loading / empty / 権限 / 境界）も受け入れ条件に含まれている。

### Gate — skeleton の要否判定
- 各サブシステムが高リスク（新規性・影響範囲・手戻りコスト）かを見極め、skeleton の要否を決定（判定基準は §3）。
- **判定主体**: orchestrator インライン（§5-B。サブエージェント化しない）

### Phase 2 — ウォーキングスケルトン（条件付き・高リスク時のみ）
- 最もリスクの高い機能横断パスを1本だけ、最小実装で端から端まで（E2E）貫通させ、「この構造は振る舞いを支えられるか」を検証。
- **起動**: `skeleton-runner`（§5-C）
- ここを通せば、残りの構造は正当に粗いモードで固めてよい。

### Phase 3 — 構造整合ループ（スライス）
- 機能に対応する DB・**処理インターフェース契約（request / response）** を作り、参照整合（互いに正しく参照し合う状態）を取る。契約は UI と処理の境界を固定する第一級の成果物で、後続の UI 実装・処理実装が唯一の拠り所とする。**UI の設計ドキュメントは作らない**（画面・UI状態は SSOT の機能詳細＝GWT に列挙済み。見た目は Phase 4 の実装で立ち上げ、人間が一瞥する）。
- **producer は2つに分ける**（正しさのオラクルが違うため。配線は §5）:
  - **DB 設計 = `db-designer`（§5-D1, 🙋 人間ゲート）** … モデリングの妥当性は機械で反証できない。ドラフトを返し人間確認。
  - **契約 = `contract-author`（§5-D2, 🤖 機械オラクル）** … 人間承認済みの機能詳細（SSOT）と DB から導出し、spec-lint と参照整合で自律的に詰める。
- **起動順**: DB を人間確認で `fixed` 化 → SSOT＋DB を入力に `contract-author` が契約を確定 → 完了後に**別コンテキスト**で `structure-oracle`（§5-E）が独立判定。契約は 1 機能 1 ファイルなので、**スライスが複数機能を含むときは `contract-author` を機能単位の並行 Task で起動してよい**（判定は全契約が揃ってから structure-oracle 1 回）。
- **完了条件**: オラクルが参照の不整合を1件も発見できなくなるまで反復（全機能が実在するエンティティを参照、SSOT が定義する全画面が実在する機能を参照、**契約が全機能の入出力を過不足なく表現している** 等）。判定は producer 自身にさせない。

### Phase 4 — 振る舞い実装ループ（スライス・契約を共有する frontend/backend 2トラック）
Phase 3 で固定した処理インターフェース契約を土台に、frontend と backend を別コンテキストで並行実装する。契約を挟んで両側を別々に作る、が核（§1 コア制約6）。frontend トラックはさらに「見た目 → 配線」に分ける（オラクルが違い、見た目だけ先に作れるようにするため）。

- **Phase 4a — frontend トラック**（見た目 → 配線の順）:
  - **4a-1 見た目**: 契約の response 形に沿って html/css/js を作る。データは契約通りにモック。**ロジックは書かない。** **起動**: `frontend-ui-implementer`（§5-G1）。ここだけ単独起動すれば「見た目だけ先に確認」ができる。
  - **4a-2 frontend 処理**: 契約の request/response に沿って、リクエスト処理・状態・純粋関数を Red → Green → Refactor で作り、見た目に配線する。**起動**: `frontend-logic-implementer`（§5-G1b）。
- **Phase 4b — backend トラック**: 契約の request/response に沿って、バックエンド処理・純粋関数を Red → Green → Refactor で作る。**起動**: `backend-logic-implementer`（§5-G2）。frontend トラックと並行。
- **結合（by-design：専任工程を置かない）**: frontend-logic が実装する API クライアントは**契約準拠の実物**であり、`モック` は frontend ロジックテスト専用にすぎない。したがって組み上がったスライスは、実行時に自動で実 backend を叩く——**mock→実 backend へ差し替える別工程・別 producer は不要**。両者が契約を守っていれば食い違わず、**結合が壊れていれば `slice-attacker` の本番相当 E2E（実 I/O・実結合）で露見する**（肯定的な "結合 OK" 判定を置くのではなく、実結合を攻撃して壊れなければ通過。テスト内モックのまま本番が動くわけではない）。
- **起動順**: `test-designer`（§5-F, 独立。契約とGWTから Red を起こす）を **UI表示／frontend処理／backend処理のトラック別に 3 並行で Task 起動**する（サブエージェントは途中報告できないため、1 体に 3 トラックを直列で書かせると両実装トラックのブロッカーになる。分割起動が唯一の並行化手段）→ **backend テスト受領で 4b を即開始、UI表示テスト受領で 4a-1 を即開始**（3 体全部の完了を待たない。backend は見た目にも依存しないので待たない）→ 4a-1 完了後に 4a-2（見た目へ配線。frontend処理テスト受領が前提）→ 契約で結合（上記のとおり自動）→ スライス完了ごとに `slice-attacker`（§5-H）。
- **重要**: テストは GWT と契約から起こす。実装を見て書かせない。テスト設計・見た目・frontend処理・backend処理はすべて別コンテキストにし、誤りが重ならないようにする。契約を変えたくなったら実装を止め、Phase 3 へ差し戻す（下記 差し戻しルール）。
- **完了条件**: 見た目・frontend処理・backend処理とも契約に適合し、結合後に各機能を機能詳細と照合して整合。スライスを壊しにいっても壊れない。

### Phase 5 — スライス横断で壊しにいく ＋ 横断的な非機能要件（NFR）
- スライス単位では原理的に拾えない、スライス間の相互作用・性能・セキュリティ・a11y 等、相互作用から生じる不整合を潰す。
- **起動**: `system-attacker`（§5-I）

### 差し戻しルール（影響範囲で戻り先を分岐）

実装中に SSOT 変更が必要になったら、**一旦実装を止めて SSOT を直してから戻る。** 戻り先は変更の影響範囲で分岐する。

| 変更の種類 | 戻り先と再検証範囲 |
|---|---|
| 振る舞いだけの SSOT 変更 | 現在のスライスに戻る |
| 固めた構造に触る SSOT 変更 | ①基準SSOTを更新 → 該当スコープの構造整合（Phase 3）を再実行 → **完了済みスライスの整合も再検証** |

「一律で元のループへ戻す」は禁止。構造変更が過去のスライスを黙って壊すため。影響範囲の判定は orchestrator インラインで行う（§5-J）。

## 5. サブエージェント起動の配線（.claude/agents/develop/ を SSOT とする）

> **各エージェントの system prompt（人格・ミッション・停止条件）は `.claude/agents/develop/*.md` が SSOT。** ここには**配線だけ**を置く（どの局面で・どれを・どの順で起動するか、独立性、人間ゲート）。ミッション本文をここに複製しない。
> 各エージェントは**別コンテキスト（Task ツール）**で起動する。親（orchestrator）は入力として SSOT の該当部分を渡す。

### 起動シーケンス早見表

### アーキタイプ（正しさのオラクルは2種類）

成果物の正しさを**誰が反証できるか**で振る舞いが決まる（§1 コア制約3）。

- **🤖 機械オラクル・ループ** — テスト・型・lint・スキーマ検証で反証できる成果物（契約・純粋関数・処理・テスト）。人間を挟まず、機械オラクルが緑になるまで自律で回す。tool は Read/Bash 中心に絞る。
- **🙋 人間ゲート** — 機械では反証できない成果物（機能要件・UI・DB設計）。producer はドラフトを返して**停止**し、orchestrator が人間に確認して `docs/spec` を `fixed` 化する。**これが §1.5 実装着手ゲートの発火点。**
- **🔴 レッドチーム／独立判定** — producer と別コンテキストで「壊す・不整合を暴く」側。read-only ＋ 実行に tool を絞り、修正はさせない。
- **🔬 探索（使い捨て producer）** — skeleton-runner のみ。構造が振る舞いを支えられるかを検証するため、別コンテキストで最小実装を書いて E2E 貫通させる。判定役ではなく作る側なので read-only ではなく Write を持つ**例外**だが、成果物は使い捨てで本線に残さない。
- **🛠 副作用実行（委譲実行）** — committer。orchestrator が自分では行わない副作用（git 操作）を、意図を受け取って実行する専任の手足。read-only 管理者である orchestrator の代理として副作用だけを起こす。入力は「意図＋対象」、出力は「実行結果＋（越権に触れたら）停止・差し戻し理由」。

### 人間ゲートの実装（Claude Code の制約に注意）

**サブエージェントはユーザーと直接対話できない**（結果を orchestrator に返すだけ）。ユーザーと話せるのは orchestrator のみ。したがって 🙋 のエージェントは自己承認せず「ドラフト＋人間が確定すべき論点」を返して停止し、**確認の儀式（AskUserQuestion / plan mode）と `fixed` 化は orchestrator が行う**。人間ゲートをサブエージェント内に埋め込まない。

### 攻撃予算（attacker のオープンエンド探索に上限を与える）

attacker（H / I）には**攻撃予算（そのラウンドで実行する攻撃の本数上限）**を必ず入力で渡す。予算のない「徹底的に」は 1 起動のウォールクロックを無制限にする最大要因のため。

- **デフォルト（初回ラウンド）**: slice-attacker **10 本**／system-attacker **15 本**。orchestrator はスライスの規模で微調整してよいが、**渡さない・無制限にすることは禁止**。
- attacker は候補を計画で出し切ったうえで優先度順に予算内を実行し、**予算外の候補を「未実行候補（優先度つき）」として必ず報告する**（無言の切り捨て禁止）。追加ラウンドの要否は orchestrator が受信時に判断する（受信アクション表）。厳密性は「深さを削る」のではなく「実行の続きを orchestrator の判断に委ねる」ことで保つ。
- **再攻撃ラウンド（欠陥修正後）**は初回計画をやり直さず、「修正の裏取り＋修正の影響経路＋回帰 smoke」に絞る。

### orchestrator インライン（ファイル化しない 2 つ）

B（skeleton 要否判定）と J（差し戻し判定）は、どの producer をどう起動するかを選ぶ**メタ判断**であり、producer とは別主体にする必要が薄い。orchestrator 自身の推論として持つ。

- **B skeleton 要否判定** — Phase1 完了後・Phase3 開始前。各サブシステムの新規性・影響範囲（blast radius）・手戻りコストを見極め、高リスクな部分に skeleton を先に通すか決める。デフォルトは skeleton なし（判定基準は §3）。**高リスクと判定したら、最もリスクの高い機能横断パスを1本 orchestrator が選び、skeleton-runner に入力として渡す。**
- **J 差し戻し判定** — 任意フェーズで SSOT 変更が必要になった時。影響範囲を判定し、振る舞いだけの変更なら現スライスへ、固めた構造に触る変更なら基準SSOT更新 → 該当スコープの構造整合（Phase3）再実行 → **完了済みスライスの整合も再検証**（差し戻しルールは §4）。

### orchestrator の受信時アクション（停止・報告の出口）

各サブエージェントは「禁止と停止」「出力」の条件で orchestrator に返す。**唯一の分岐基準は「修正が人間オラクル成果物に及ぶか」。**

**人間を必ず通す3つ（人間オラクル成果物）。この作成・変更は例外なく承認を得る:** ① SSOT（機能一覧・機能詳細／GWT） ② UI の見た目 ③ DB 設計。
**それ以外はすべて機械＋AIで回す（人間を挟まない）。** SSOT を正とすれば、契約・純粋関数・テスト・実装・結合は決定論的に反証可能（テスト・型・lint・spec-lint・参照整合）だからだ。

**差し戻し・再判定はラウンド制で回す（往復回数を最小化する）:**

- 判定役（oracle / attacker）の指摘は、**同一ラウンドの全件をまとめて 1 回で**該当 producer へ差し戻す（**1 欠陥 1 往復を禁止**）。producer は全件を 1 回の起動で修正して返す。
- 再判定・再攻撃も**ラウンド単位で 1 回だけ**起動する（欠陥 1 件直すごとに判定役を起動しない）。
- **2 周目以降の判定役には「前回の指摘リスト＋今回の変更範囲」を入力で渡し**、判定スコープを「修正の裏取り＋変更の影響範囲の再走査」に絞る（初回はフル判定。判定主体の独立は変えない——狭めるのはスコープだけ）。

| 受信する停止・報告 | 発信元 | 出口（🙋 人間／🤖 機械＋AI） |
|---|---|---|
| ドラフト＋確認論点（機能一覧・詳細） | ssot-definer | 🙋 人間に提示 → 承認で `fixed` 化・次フェーズへ／修正指示で producer 再起動 |
| ドラフト＋確認論点（DB 設計） | db-designer | 🙋 人間に提示 → 承認で `fixed` 化／修正指示で再起動 |
| 見た目＋確認依頼 | frontend-ui-implementer | 🙋 人間に見た目を提示 → 承認で確定／修正指示で再実装 |
| 契約を確定できない（機能/DB の欠陥が原因） | contract-author | 🙋 原因の人間オラクル（①機能詳細 or ③DB）へ差し戻し → 承認後に契約を再導出 |
| 契約の補足（承認済み SSOT＋DB から導出可能） | contract-author | 🤖 contract-author を再起動して補い、structure-oracle が再判定 |
| 不整合リスト | structure-oracle | 🤖 **全件を 1 ラウンドで**該当 producer へ差し戻し → **差分スコープで**再判定、空までループ（原因が①〜③なら🙋へ） |
| GWT/契約の不足 | test-designer | 原因が SSOT → 🙋／契約 → 🤖 再導出 |
| 契約に不足（実装中） | 3実装体 | 契約内で閉じる → 🤖 補正＋再配線／①〜③に及ぶ → 🙋 |
| テスト赤・攻撃成功 | 実装体／slice・system-attacker | 🤖 **指摘全件を 1 ラウンドで**実装体へ差し戻し → 修正 → **差分スコープで**再テスト/再攻撃、空までループ（原因が①〜③なら🙋） |
| 攻撃報告に未実行候補（予算外） | slice・system-attacker | 🤖 高優先の候補が残っていれば追加ラウンド（残予算と候補を渡して再起動）／残っていなければ通過。**無言で切り捨てない** |
| 構造反証 | skeleton-runner | 原因が DB 等の構造 → 🙋／その他 → Phase1/3 で作り直し |
| commit 結果（sha／PR URL）or 停止＋差し戻し理由 | committer | 🛠 実行結果を記録。停止時は理由に応じ対応（分割方針を指示して再委譲／フック落ちがコード・仕様修正を要するなら該当 producer へ差し戻し）。commit の成否は🙋に上げない |
| ADR ファイル or 記録不能（決定が未確定） | adr-writer | 🛠 記録結果（ADR 番号・supersede）を残す。決定が未確定・トレードオフ不明で書けない時は🙋人間へ |

- **差し戻しの戻り先・再検証範囲は §4 差し戻しルールに従う。**
- **判定は必ず独立役に再度させる。** orchestrator が自分で直して自分で OK にしない（コア制約3）。
- **機械で回せる出口を人間に上げない。** テスト赤・lint・参照不整合・契約内で閉じる補正は🙋を挟まず🤖で回す（①〜③に波及した時だけ人間へ昇格）。

## 6. プラットフォーム / framework 固有規約（orchestrator が解決して渡す）

producer（実装・DB 設計・テスト設計）を起動する前に、対象の platform/framework を判定し、該当する**規約葉のパスを解決して各 producer の入力に渡す**（agent 自身にカタログを辿らせない）。**配送は「パス渡し」に一本化する** — orchestrator が解決済みの1本のパスを Task 入力に載せ、producer 側が着手前にそれを Read する。葉を唯一の SSOT に保ち、中身をコピペして drift させない。渡されたパスの Read はカタログ探索ではないので許可される。

> **なぜインライン展開でなくパス渡しか。** これらの葉は非常駐（`paths:` gate）で、native の paths ゲートは sub-agent の自コンテキストでも発火する（＝マッチするソースを Read した瞬間に注入される）が、それは**遅延**（読んだ後）で**宛先も glob 任せ**。greenfield の test-designer は「書く→後で発火」で手遅れになり、testing 規約が test-designer に届く保証もない。だから明示ハンドオフ（パス渡し）を**正**とし、native paths ゲートはその上に乗る**無償の安全網**とする（渡し忘れても実装体がソースを触れば救われる）。インライン展開（本文を prompt に貼る）は prompt を肥大させ SSOT を割りうるので、worktree isolation 等でパスが揺れる特殊時の代替に留める。

**規約は成果物ごとに宛先が違う**ので、下表の「渡す先」に沿って配る。

| platform / framework | 参照する箱 / 葉 | 渡す先 |
|---|---|---|
| Web / crow（PHP） | [crow/overview.md](../../rules/develop/web/crow/overview.md)（[coding.md](../../rules/develop/web/crow/coding.md) / [testing.md](../../rules/develop/web/crow/testing.md) / [db.md](../../rules/develop/web/crow/db.md)） | coding → 実装3体（frontend-ui / frontend-logic / backend-logic）／testing → test-designer／db（`db_design.txt`） → db-designer |
| Native | （未登録 — 規約が無ければ渡さない） | — |

- **coding 規約**は表面（html/css/js）も含むので frontend 実装体にも渡す（backend だけではない）。
- **testing 規約（PHPUnit 等）は Red を書く test-designer に渡す**（テストを緑にする実装体ではなく、起票する側が従う）。
- **DB 設計のネイティブ書式・住所は db-designer に渡す**（§4 docs 住所表のとおり、マイグレーション元があればそれが唯一の SSOT）。
- 該当 framework が無ければ、framework 固有規約は渡さない（無いものを捏造しない）。

---

## 7. 完成条件（最終ゲート）

以下がすべて満たされた時のみ「完成」とする。

- [ ] 全機能が基準SSOTに列挙され、各機能に反証可能な GWT がある。
- [ ] Phase 3 で各機能の処理インターフェース契約が確定し、構造整合オラクルが参照・契約の不整合を発見できない。
- [ ] 全スライスで UI・処理がともに契約に適合し、テスト緑、かつ結合後に機能詳細と整合。
- [ ] 攻撃エージェントがどのスライスも壊せなかった。
- [ ] 横断反証エージェント（system-attacker）が、相互作用から生じる不整合・NFR違反を発見できなかった。
- [ ] 実装中に発生した全 SSOT 変更が差し戻し処理され、影響を受けるスライスが再検証済み。

**「テストが全部通ったから完成」は完成条件ではない。** 独立した攻撃を本番に最も近い環境で試みて壊れなかったことが、唯一の完成条件である。
